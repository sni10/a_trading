# План реализации бэктеста

**Дата:** 2026-05-31
**Статус:** Черновик плана (реализация не начата)
**Область:** Добавление офлайн-бэктеста поверх существующего торгового конвейера без переписывания домена.

---

## 1. Зачем это нужно (постановка проблемы)

Ценность торгового бота — в **эдже стратегии**, а не в качестве кода. Сейчас в проекте:

- стратегия (`IndicatorSignalService`: MACD + SMA-7/SMA-25 → BUY/HOLD) **никак не провалидирована** на исторических данных;
- нет ответа на главный вопрос: **«эта логика в принципе плюсовая или сливает депозит на комиссиях и спреде?»**.

Без бэктеста любая доработка боевого исполнения — это вложения в мотор, про который неизвестно, едет ли он вперёд.

**Цель бэктеста:** прогнать боевой конвейер принятия решений на исторических данных и получить метрики прибыльности (PnL, winrate, число сделок, просадка) с учётом комиссий.

---

## 2. Что уже готово (сильная сторона архитектуры)

Главное звено — `TickPipelineService.process_tick()`
(`src/application/services/ticker_pipeline_service.py`) — **чистое, без I/O, сети и файлов**.
Весь цикл `FEEDS → IND → STRAT → ORCH → EXEC → STATE` работает поверх in-memory `context`.

Следствия:

- бэктест переиспользует **тот же** код принятия решений 1:1 — не будет расхождения «бэктест-движок vs продакшен-движок»;
- таймауты протухших ордеров (`cancel_stale_buy_orders`) завязаны на `ts` из тика, а не на `time.time()` → в бэктесте отработают корректно при подаче исторических таймстампов;
- индикаторный движок (`IndicatorEngine`, история 500 точек) работает поверх потока цен и не требует изменений.

## 3. Чего не хватает для бэктеста (ядро задачи)

| # | Пробел | Где сейчас | Что нужно |
|---|--------|-----------|-----------|
| 1 | **Нет симулятора исполнения (fill engine)** | `execute()` (`src/domain/services/execution/execution_service.py`) только создаёт `buy`/`sell` ордера в статусе `open`; в бою их «заполняет» биржа через `order_sync_worker` | Компонент, который на каждом тике помечает ордера filled по пересечению цены и закрывает сделку |
| 2 | **Нет учёта PnL / метрик** | нигде | Сборщик результатов: итоговый профит, winrate, число сделок, max drawdown, комиссии, equity-кривая |
| 3 | **Нет загрузчика истории** | `IExchangeConnector` содержит только `stream_ticks` + `fetch_order_book` (`src/domain/interfaces/exchange_connector.py`) | Метод `fetch_ohlcv` в интерфейсе + реализация в `CcxtProExchangeConnector` + кэш в файл/БД |
| 4 | **Нет источника исторических «тиков»** | `TickSource.stream()` ходит в живой коннектор (`src/domain/services/ticker/ticker_source.py`) | `HistoricalTickSource`: свеча → доменный `Ticker` (`close` свечи как `last`) |

## 4. Важные нюансы и ограничения (честно)

1. **Tick-based vs bar-based.** Боевой конвейер работает на реальных тиках (поток `last`-цен).
   Исторические данные доступны только как свечи (OHLCV). В бэктесте `close` каждой свечи подаётся
   как «тик» → MACD/SMA будут считаться по барам, а в бою — по тикам. Поведение немного разойдётся.
   Для вопроса «плюсовая ли логика в принципе» этого достаточно; для точного прогноза доходности — нет.

2. **Модель филлов — упрощённая (оценка «сверху»).** Базовая версия закрывает ордер по факту
   пересечения ценой свечи уровня ордера. Не моделируются: частичные исполнения, проскальзывание,
   глубина стакана, очередь в лимитном ордере. Реальные результаты будут **не лучше** бэктеста.

3. **Комиссии — обязательны.** Без учёта `buy_fee_percent` / `sell_fee_percent` бэктест соврёт в плюс.
   Брать те же значения, что использует `StrategyCalculator` в боевом расчёте.

4. **Orderbook-фильтр.** `DecisionCenter` отклоняет BUY при «плохом» стакане
   (`OrderBookSignal.REJECT/WEAK_SELL/STRONG_SELL`). Исторического стакана у нас нет.
   Варианты: (а) в бэктесте подавать нейтральный/пропускающий стакан; (б) синтезировать стакан из свечи.
   Решение: для MVP — нейтральный стакан (фильтр не режет), отметить это как допущение.

5. **Балансы.** `RiskManager` читает `context["balances"]`, которые в офлайне не заполняются.
   В бэктесте задавать стартовый баланс явно (конфиг бэктеста) и обновлять его в fill-симуляторе.

## 5. Архитектура решения

Соответствие гайдлайнам: новый код — в `application/` (use case + сервисы), домен правится минимально
(только добавление метода в интерфейс), DI сохраняется, файлы < 200 строк, методы < 50.

```
src/
├── domain/
│   └── interfaces/
│       └── exchange_connector.py      # + fetch_ohlcv(...) (расширение контракта)
│
├── infrastructure/
│   └── connectors/
│       └── ccxt_pro_exchange_connector.py   # + реализация fetch_ohlcv через ccxt
│
└── application/
    ├── backtest/                      # НОВЫЙ пакет
    │   ├── __init__.py
    │   ├── historical_tick_source.py  # OHLCV → поток доменных Ticker
    │   ├── fill_simulator.py          # закрытие buy/sell по пересечению цены
    │   ├── metrics_collector.py       # PnL, winrate, DD, equity-кривая
    │   ├── backtest_config.py         # dataclass: символ, период, баланс, комиссии, таймфрейм
    │   └── backtest_runner.py         # оркестрация: data → process_tick → fills → metrics
    └── use_cases/
        └── run_backtest.py            # entrypoint use case

backtest.py                            # тонкий CLI-фасад в корне (по аналогии с main.py)
data/ohlcv_cache/                      # кэш скачанных свечей (gitignore)
```

### Поток данных

```
fetch_ohlcv (с кэшем)
   → HistoricalTickSource: свеча → Ticker
      → BacktestRunner (цикл по тикам):
           process_tick(context, ...)        # боевой конвейер: индикаторы → стратегия → решение → EXEC(open-ордера)
           FillSimulator.on_tick(context)    # пометить filled, закрыть deal, обновить баланс
           MetricsCollector.record(context)  # снять equity / зафиксировать сделку
      → MetricsCollector.report()            # итоговый отчёт
```

## 6. Этапы реализации

### Этап 1. Загрузка исторических данных
- Добавить `fetch_ohlcv(symbol, timeframe, since, limit)` в `IExchangeConnector`.
- Реализовать в `CcxtProExchangeConnector` через ccxt `fetch_ohlcv` с постраничной докачкой.
- Кэш свечей на диск (`data/ohlcv_cache/`), чтобы не дёргать биржу при каждом прогоне.
- Тест: загрузка + чтение из кэша (без реальной сети — мок коннектора).

### Этап 2. Источник исторических тиков
- `HistoricalTickSource`: маппинг OHLCV-свечи в доменный `Ticker` (`last = close`, `ts = candle ts`).
- Тест: корректность маппинга, монотонность таймстампов.

### Этап 3. Симулятор исполнения (ядро)
- `FillSimulator.on_tick(context, price, ts)`:
  - BUY-ордер `open` и `price >= buy_order.price` (лимит на покупку дешевле) → filled, списать средства + комиссию;
  - SELL-ордер `open` и `price >= sell_order.price` (тейк) → filled, закрыть deal, зачислить выручку − комиссию;
  - корректно переводить статусы Order/Deal согласно их методам (`is_open/is_closed`, lifecycle Deal).
- Тест: сценарии «купил→продал в плюс», «купил→таймаут отменил», «не купил».

### Этап 4. Сбор метрик
- `MetricsCollector`: число сделок, winrate, суммарный/средний PnL (с комиссиями), max drawdown, equity-кривая, итоговый баланс vs стартовый.
- Тест: метрики на синтетической серии сделок с известным ответом.

### Этап 5. Раннер и CLI
- `BacktestRunner` склеивает источник → `process_tick` → `FillSimulator` → `MetricsCollector`.
- `run_backtest` use case + `backtest.py` CLI:
  ```powershell
  python backtest.py BTC/USDT --from 2025-01-01 --to 2025-03-01 --timeframe 1h --balance 1000
  ```
- Вывод: текстовый отчёт в консоль (+ опционально CSV equity-кривой).

### Этап 6. Первый прогон и интерпретация
- Прогнать текущую MACD+SMA стратегию на 2–3 месяцах BTC/USDT.
- Зафиксировать цифры в отдельном отчёте.
- Вывод: плюсовая логика или нет → решение, доделывать ли боевой контур.

## 7. Критерии готовности (Definition of Done)

- [ ] `python backtest.py BTC/USDT --from ... --to ...` отрабатывает end-to-end на закэшированных данных.
- [ ] В отчёте есть: итоговый PnL (с комиссиями), число сделок, winrate, max drawdown.
- [ ] Бэктест переиспользует `process_tick` без копии логики стратегии.
- [ ] Все новые модули покрыты юнит-тестами (fill-симулятор и метрики — в первую очередь).
- [ ] Допущения (bar-vs-tick, упрощённые филлы, нейтральный стакан) явно перечислены в выводе/README.
- [ ] Соблюдены гайдлайны: домен не импортирует infrastructure, файлы < 300 строк, методы < 50.

## 8. Что НЕ входит в этот план (осознанные исключения)

- Точное моделирование микроструктуры рынка (очередь лимитника, частичные филлы, проскальзывание).
- Бэктест на реальных тиках (только свечи).
- Оптимизация/перебор параметров стратегии (grid/walk-forward) — отдельная задача после MVP.
- Учёт исторического стакана (нет данных) — используется нейтральное допущение.

## 9. Риски

| Риск | Митигация |
|------|-----------|
| Бэктест покажет плюс, а в бою будет минус (overfit / завышенная модель филлов) | Честно маркировать как оценку «сверху»; далее — forward-test на testnet |
| Расхождение bar-vs-tick исказит сигналы | Зафиксировать как допущение; при необходимости — переход на тиковые данные позже |
| Скрытые зависимости `process_tick` от боевого окружения (логгер, воркеры) | Конвейер уже заявлен как чистый; проверить на первом интеграционном прогоне |
| Неверный учёт комиссий → ложный плюс | Брать комиссии из того же источника, что и `StrategyCalculator`; покрыть тестом |
